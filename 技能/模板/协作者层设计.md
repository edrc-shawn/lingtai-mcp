# 协作者层 — 跨客户端无缝衔接方案

> 参考来源：小耳朵 Git 映射分析 + DeepSeek-V4-Pro / MiniMax-M3 / GLM-5.2 / Qwen3.7-Max / Kimi-K2.7-Code 五模型对比

## 一、问题

| 问题 | 表现 |
|------|------|
| 角色模糊 | 灵识规则说「灵识是后台进程」，但同一个 AI 既在做事又在记忆，边界不清 |
| 记忆碎片 | Reasonix 自有记忆 (remember) 和灵识记忆 (memory_write) 两本账，互不同步 |
| 换客户端丢上下 | Reasonix 的记忆留在本地，换 WorkBuddy/MiMoCode 就没了 |
| 协作者无灵魂 | AGENTS.md 全是**操作规则**（怎么做），没有**人格设定**（怎么说活） |
| 场景交叉污染 | 工作场景的情绪渗入生活场景的对话，没有隔离 |

## 二、核心认知

**模型不自知。** 一个模型不知道自己叫什么、什么风格，全靠客户端 System Prompt 注入。同样的大脑，放在 Reasonix 里叫 Reasonix AI，放在 WorkBuddy 里叫 WorkBuddy 助手——两套台词。

**人格不能是模型自带的，必须是 MCP 层注入的。** 谁连接同一个 MCP Server，谁就拿到同一套人格 + 记忆 → 跨客户端无缝衔接。

**记忆不是"记得"，是"演得像记得"。** 每次对话都是重新构造的一次性叙事——持久化不在模型权重里，在外部文件里。记忆系统的价值在于**筛选什么进入上下文**，不在于存档。

## 三、方案总览

```
任何客户端（Reasonix / WorkBuddy / MiMoCode...）
        │
        ▼ 连接灵台 MCP
    context_load()
        │
        ├── 丹房知识概览         ← 已有
        ├── 灵识四层记忆         ← 已有
        ├── 协作者约束集         ← 新增【一】
        ├── 工作印记             ← 新增【二】
        └── 当前场景分支记忆     ← 新增【三】
```

### 【一】协作者约束集（Persona）

不是「语气风格」（模型间无法一致），而是**原则 + 边界**（跨模型可执行）：

| 维度 | 内容 | 跨模型一致性 |
|------|------|------------|
| 结构 | 结论先行 → 理由 → 证据 | ✅ 高 |
| 输出 | 能用列表不用段落 | ✅ 高 |
| 禁则 | 不称AI、不道歉、不啰嗦、不编造 | ✅ 高 |
| 关系 | 被问方，不越界当老师 | ✅ 高 |
| 准确 | 不确定就说不知道，不猜 | ✅ 高 |
| 定位 | 我知道我是谁、我在和谁说话、我在做什么 | ✅ 高 |

存储位置：`丹房/00-思考与认知/协作者约束集.md`
注入方式：`context_load()` 时随丹房概览一起返回
维护者：用户写一次，很少改

**不写风格层的原因：**
- DeepSeek/GPT/Claude/MiMo 对「轻松活泼」理解不同
- 模型口音是自然属性，不致命，随迭代会变
- 真正的跨客户端一致性锁定在约束层，不在语气层

### 【二】工作印记（task-progress）

**目的：** 让下次会话知道「上次在做什么、到哪了」，不管换什么客户端。

| 时机 | 动作 |
|------|------|
| **收尾时**（§4.8） | `memory_write(content: "当前任务进展到X中断于Y", tags: ["协作者-工作印记"])` |
| **新会话启动**（规则④） | `memory_search(tags: ["协作者-工作印记"], min_confidence: 0.3)` 回收上次进度 |

存储位置：灵识记忆银行（已有）
标签：`tags=["协作者-工作印记"]`
维护者：AI 收尾时自动写入

### 【三】场景分支（branch）

**目的：** 不同场景的记忆不互相污染。

```
灵识记忆银行（main — 跨场景稳定事实）
├── work          ← 工作项目、甲方、决策
├── life          ← 家庭、朋友、兴趣
├── creation      ← 内容创作、选题、配图
└── thinking      ← 思考认知、哲学、追问
```

**规则：**
- 当前在讨论什么 → `checkout` 对应 branch
- `memory_write` 加 `branch` 参数，默认自动场景检测
- `memory_search` / `lingshi_inject` 默认只在当前 branch + main 中检索
- 跨场景信息通过显式 merge 共享（如"喜欢极简"从 work merge 到 main）

## 四、为什么不需要 per-client / per-model 记忆

| 方案 | 换客户端？ | 换模型？ | 复杂度 |
|------|----------|---------|-------|
| ❌ 各家配各家记忆 | 丢 | 丢 | 高（N套） |
| ✅ 统一走 MCP 层 | 不丢 | 不丢 | 低（1套） |

模型口音差异（DeepSeek 啰嗦一点 vs Claude 暖一点）是自然属性，可以接受。约束集能保证原则一致即可。

## 六、记忆版本化（git 式）

### 6.1 问题：现在覆盖式写入

当前 `memory_write` 的行为：

```
用户说"截止日期7月15号"       → memory_write("截止日期7月15号")
用户纠正"是7月20号"           → memory_write("截止日期7月20号")
                              ↑ 旧版本静默消失，追溯不到
```

覆盖式的问题：纠正不是"写错了重写"，而是"我改主意了，但改之前是什么也应该知道"。

### 6.2 方案：entries 列表（参考 Memoir facet）

不覆盖旧版本，每个 topic 下存一个时间戳 entries 列表，受 MAX_ENTRIES 限制：

```
topic_id: "deadline"
memory_type: "semantic"
merge_strategy: "confidence_gated"
entries:
  [
    {content: "截止日期7月15号",   confidence: 0.4, ts: 7/15, source: "user_stated"},
    {content: "截止日期7月20号",   confidence: 0.9, ts: 7/20, source: "user_correction"},
    {content: "截止日期7月25号",   confidence: 0.8, ts: 7/25, source: "user_stated"},
  ]
projected_content: "截止日期7月25号"  ← 置信度最高的 active entry
```

**与版本链的区别：** 版本链需要独立 memory_id + parent 指针，entries 是同一个 key 下的追加列表，简单得多。读取时取 confidence 最高的 active entry。

### 6.3 合并策略（6 种，参考 Memoir）

不同记忆类型使用不同的默认合并策略：

| 记忆类型 | 例子 | 默认策略 | 含义 |
|---------|------|---------|------|
| **WORKING** | 当前 task 上下文、暂存 | REPLACE | 最后写入覆盖，不保留历史 |
| **EPISODIC** | 对话历史、事件流 | APPEND | 追加到 entries 列表，受 cap 限制 |
| **SEMANTIC** | 事实、偏好、知识 | **CONFIDENCE_GATED** | 新置信度 >= 现有才写入 |
| **PROCEDURAL** | 技能、流程、workflow | LLM_MERGE | 新老内容让 LLM 合并 |

**6 种策略详解：**

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| **APPEND** | 追加到 entries 列表 | 事件流、对话历史 |
| **REPLACE** | 新条目替换旧条目 | 暂存、工作区 |
| **CONFIDENCE_GATED** | 新置信度 >= 现有才写入 | 事实、偏好 ← 灵台最常用 |
| **LLM_MERGE** | 新老内容由 LLM 合并后写入一条新 entry | 技能、流程 |
| **MERGE_ON_READ** | 存储时 APPEND，读取时 LLM 合并 | 需保全文档历史的场景 |
| **REJECT** | 不写入，返回冲突信息 | 用户仲裁场景 |

**核心原则：不是所有记忆都需要版本化。** WORKING 和 EPISODIC 用简单策略，SEMANTIC 做置信度门控，PROCEDURAL 用 LLM 合并——每种记忆类型有其自然的合并方式。

### 6.4 Diff-aware 写入（来自小耳朵 + 五模型共识）

写入前先 diff，不是每条都产生新 commit：

```
"老陈对极简设计偏好 +1 确认"
  → diff 检测：和 HEAD 一致
  → 不产生新 commit，只更新置信度 +1

"项目 A 甲方确认为万科"
  → diff 检测：新信息
  → 产生新 commit
```

**收益：** 同一偏好被确认 5 次不会写 5 条记录，只有一条 + 置信度递增。

### 6.5 三条工程规则

| 规则 | 说明 |
|------|------|
| **写入不覆盖** | 同 topic 的新写入 -> 追加 entries，旧条目保留 |
| **读取取投影** | memory_search / lingshi_inject 返回置信度最高的 active entry |
| **回退靠还原** | memory_revert(topic) 将指定历史 entry 重新激活（写入新 entry 复制旧内容） |

### 6.6 自动记忆类型检测

写入时根据关键词自动推断记忆类型（参考 Memoir 的 remember 自动分类）：

| 关键词 | 推断类型 | 默认策略 |
|--------|---------|---------|
| 截止日期/项目/甲方/偏好/姓名 | semantic | CONFIDENCE_GATED |
| 今天/刚才/上次/发生了 | episodic | APPEND |
| 当前任务/正在做/下一步 | working | REPLACE |
| 方法是我习惯/步骤 | procedural | LLM_MERGE |

未匹配 -> 默认 semantic（CONFIDENCE_GATED，最安全）。

### 6.7 与现有记忆系统的关系

| 组件 | 改动 |
|------|------|
| 记忆银行（memory_write） | 写入改为 entries 追加 + 记忆类型检测 + 策略选择 |
| 记忆搜索（memory_search） | 不变——返回投影（最高置信度 active entry） |
| 记忆反馈（memory_feedback） | 不变——adopt/reject 作用于当前 active entry |
| 衰减调度（mem_decay） | scope 缩小——只衰减 entries 中的 active entries，不衰减已归档 |

## 七、场景分支（Branch）

### 7.1 问题：场景交叉污染

当前记忆没有场景隔离，所有记忆混在一起。工作场景的情绪可能渗入生活场景的对话，思考认知的偏好可能污染工具使用的判断。

### 7.2 Branch 模型

每个场景一条独立分支，默认隔离，显式 merge：

```
main              ← 用户画像（跨场景的稳定事实）
├─ work           ← 工作场景：项目、甲方、决策
├─ life           ← 生活场景：家庭、朋友、兴趣
├─ creation       ← 内容创作：选题、配图、风格
└─ thinking       ← 思考认知：哲学、追问、框架
```

### 7.3 规则

| 规则 | 说明 |
|------|------|
| **场景检测** | 新会话启动时，根据上下文自动判断当前场景，checkout 对应 branch |
| **默认隔离** | branch 之间的记忆默认不互相可见 |
| **显式 merge** | 跨场景共享的信息（如"老陈喜欢极简"）通过 merge 进入 main |
| **无 branch 参数** | 写入时不指定 branch → 自动场景检测 + 写入对应 branch |

### 7.4 Merge Conflict 处理

跨模型共识：**语义合并冲突是核心难题。**

| 冲突类型 | 策略 | 参考来源 |
|---------|------|---------|
| **加性事实**（"会Python"+"会Go"） | 自动合并，不冲突 | MiniMax-M3: CRDT |
| **互斥事实**（"偏好A" vs "偏好B"） | 标记冲突，下次对话时让 LLM 判断是否需向用户确认 | 小耳朵: merge conflict 标记 |
| **价值层冲突**（风格/原则矛盾） | 必须用户仲裁，不做自动合并 | Kimi-K2.7-Code |
| **结构化记忆** | 用规则自动合并 | GLM-5.2 |
| **非结构化记忆** | LLM 作为 merge 裁判 | GLM-5.2 |

### 7.5 实施约束

| 约束 | 原因 |
|------|------|
| 分支不自动创建 | 用户或 AI 显式指定时才新建 |
| main 分支只读merge | 只有确认的跨场景事实才能进 main |
| 分支可删除 | 已结束的项目分支用户可删除，但删除前确认是否需 merge 到 main |

## 八、遗忘（主动归档）

### 8.1 问题：现在的衰减是被动的

规则⑧有 `mem_decay`（按时间衰减置信度），但衰减到 0 不等于"遗忘"——条目仍占存储空间，仍可能被搜索到，只是置信度低。

真正的遗忘是：**判断这条记忆的预期寿命到了，主动归档，不再参与搜索和注入。**

### 8.2 三类遗忘策略

| 类型 | 触发条件 | 行为 |
|------|---------|------|
| **一次性** | 单次任务完成 | 显式标记 `obsolete`，归档 |
| **衰减到期** | 条目的 active entry 置信度连续低于阈值 N 个周期 | 自动归档 |
| **超限裁旧** | entries 列表超过 MAX_ENTRIES（默认50） | 裁最旧的 entry，不影响 active entry |

### 8.3 冷热分层

```
活跃池（热）: 常被引用、高置信度、最近写入
    │
    ├── 自动注入（lingshi_inject 的默认范围）
    ├── 参与搜索（memory_search 的默认范围）
    └── 参与衰减（mem_decay 的调度范围）
    │
    ▼
冷存储（冷）: 已归档条目
    │
    ├── 不自动注入
    ├── 可手动搜索（memory_search(include_archived=true)）
    ├── 不参与衰减
    └── 可恢复（memory_revert 或重写）
```

### 8.4 遗忘与版本化的配合

**有 git 无遗忘** → 版本链越长，存储越大，早晚爆仓
**有遗忘无 git** → 衰减错了？没了就真没了

```
版本化 → 让你敢遗忘（反正能回退）
遗忘   → 让版本链有意义（不用的版本归档，不占活跃池）
```

用 git 类比：**`git gc` 不是 bug，是 feature。**

### 8.5 实施约束

| 约束 | 原因 |
|------|------|
| 归档不自动删除 | 物理删除不可逆，归档是逻辑删除，参考 Kimi: 完整提交历史可能成为泄露源 |
| 版本链归档 = 旧版本全部归档 | 活跃池只保留最新版本 |
| 归档可恢复 | 用户触发回退后自动从冷存储还原 |
| 不增加新工具 | 内置在 `memory_write` 和 `mem_decay` 中 |

## 九、Git 原语到记忆系统的完整映射

（来自小耳朵的 Git 映射分析，五模型交叉验证）

| Git 概念 | 记忆系统对应 | 解决什么问题 | 实现优先级 |
|---------|-------------|------------|----------|
| **commit** | 记忆写入的原子操作，含时间戳 + diff + 作者 | 可追溯 | P0 |
| **blob / tree** | 碎片内容 / 碎片之间的组织结构 | 内容和结构分离 | P2 |
| **branch** | 并行场景线（工作/生活/项目） | 场景隔离 | P1 |
| **merge** | 跨场景信息整合，冲突时显式标记 | 矛盾不自动覆盖 | P1 |
| **rebase** | 记忆重写：用最新理解重新解释历史碎片 | 碎片不变，解释层更新 | P2 |
| **cherry-pick** | 选择性检索：从某条场景线精准提取一条记忆 | MMR 选片的工程实现 | P2 |
| **stash** | 临时上下文：对话中产生的半成品想法 | 不污染主线的轻量暂存 | P2 |
| **tag** | 里程碑快照："MVP 阶段"、"换工作" | 时间轴的语义锚点 | P3 |
| **blame/log** | 每条记忆的溯源 | 可信度的元信息 | P1 |
| **revert** | 回滚一条错误记忆写入 | 纠正不覆盖 | P0 |
| **.gitignore** | 明确不记忆的内容类型（闲聊、一次性指令） | 防污染 | P1 |
| **diff** | 写入前对比，重复的不产生新记录 | 去重+置信度更新 | P1 |
| **gc** | 遗忘归档，冷热分层 | 存储管理 | P1 |

### 优先级说明

**P0（马上做）：** commit（append-only 写入）、revert（回退）
**P1（紧接着做）：** branch（场景隔离）、diff（去重）、blame/log（溯源）、.gitignore（防污染）、gc（遗忘）
**P2（后续）：** cherry-pick（精准检索）、stash（暂存）、rebase（重写解释）
**P3（远期）：** tag（里程碑）、tree（内容结构）

## 十、工程参考：五模型方案对比

### 10.1 各模型独特贡献

| 模型 | 独特贡献 | 适合什么 |
|------|---------|---------|
| **DeepSeek-V4-Pro** | 工作区/暂存区/仓库三层模型 | 概念理解与灵感激发 |
| **MiniMax-M3** | CRDT、事件溯源、S3+SQLite 最小实现栈 | 工程参考与实现方向 |
| **GLM-5.2** | 文档级 vs 条目级版本控制双路线 | 架构设计决策支持 |
| **Qwen3.7-Max** | rebase/cherry-pick/blame 映射最全 | 概念覆盖面 |
| **Kimi-K2.7-Code** | 隐私安全风险、轻量级折中方案 | 风险与可行性评估 |

### 10.2 共识与分歧

**共识：**
- 语义合并冲突是核心难题
- 记忆应从"覆盖式"转向"追加式演化"
- 分支可实现多场景/多角色记忆隔离

**关键分歧：**
- **合并策略：** CRDT（MiniMax）vs 规则+LLM 裁判（GLM）vs 时间衰减+上下文匹配（Qwen）vs 用户仲裁（Kimi）
- **对 Git 的态度：** 完整移植哲学（DeepSeek/Qwen）vs 借鉴思想（MiniMax）vs 轻量级重构（Kimi）
- **存储方案：** 文档级 vs 条目级（GLM）vs S3+SQLite（MiniMax）

### 10.3 本方案的选择

| 选择点 | 我们的立场 | 理由 |
|-------|----------|------|
| 对 Git 的态度 | 借思想，不套实现 | 灵台不需要完整 Git 引擎，JSONL 文件 + diff 逻辑即可 |
| 存储粒度 | entries 列表（topic 级） | 同一 topic 下存 entries 列表，取代独立 version chain |
| 合并策略 | 6 种策略 + 按 memory_type 分配默认策略 | 借鉴 Memoir 的 CONFIDENCE_GATED / APPEND / REPLACE / LLM_MERGE / MERGE_ON_READ / REJECT |
| 源数据 | 灵感来自 Memoir 真实实现 + DeepSeek 三层模型 | 已验证的生产级实现 |
