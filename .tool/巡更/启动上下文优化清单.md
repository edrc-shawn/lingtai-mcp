> 目的:把每周一「灵台·每周查」自动化跑起来前,先搞清楚新会话到底被塞了多少上下文、哪些是噪音。
> 场景:WorkBuddy 桌面端 + 灵台 MCP(`context_load` 启动协议)。
> 测量日期:2026-07-20。

## 二、可发给 WorkBuddy 的优化清单(按性价比排序)

### P0 — 零风险、立省
1. **`connector-status` 全 disconnected 时不注入或折叠**
   - 现状:58 条 `xxx: disconnected` 占 ~1,850 字符,本会话一眼未用。
   - 建议:仅当存在 `connected` 状态时注入;全断时输出一行占位(如 `connectors: all disconnected (58)`)。
   - 预计节省:~1,800 字符 / ~1,200 token。

2. **各类 reminder 块合并为单一「规则摘要」**
   - 现状:`memory_and_skills_reminder`、`instructions_for_visualizer`、`tool_usage_policy` 等散落多处,重复提及「记忆」「skill」规则。
   - 建议:折叠成一处索引,详细规则仅当相关工具被调用时展开。
   - 预计节省:~1,000 字符 / ~700 token。

### P1 — 低风险、需评估
3. **`AGENTS.md` 再瘦身**
   - 现状主信标 8,143 字符,P0 规则摘要表 + 灵识约束集已较全。
   - 建议:把「实操速查」「提炼全流程」等步骤性内容下沉到 appendix(已部分做),主文件只留导航 + 硬规则。
   - 预计节省:~2,000–3,000 字符 / ~1,500–2,000 token。

4. **技能/工具清单懒加载**
   - 现状:`available_skills`(25)+`available_deferred_tools`(60)+ 主 schema 全量注入。
   - 建议:会话开头只给工具名索引;schema 详情在首次调用某工具前再注入(类似 MCP 的 lazy schema)。
   - 预计节省:~5,000–20,000 字符 / 视机制而定。

### P2 — 灵台侧自查(不依赖 WorkBuddy)
5. **审计 `context_load` 实际返回体量**
   - 画像三层(履历/心性/我是谁)是否需全量?教训(`mem_query tags=lesson`)是否真按需?
   - 若某子块长期零命中,改为「命中才展开」。
   - 这是灵台可控项,无需 WorkBuddy 改。

6. **`MEMORY.md` 已压到 2,356 字符(✅ 完成)**,下次会话不再被截断。

## 三、结论

- **真正的「塞太多」元凶**:`connector-status`(纯噪音)+ 工具目录全量注入(功能性但体量大)。
- **灵台 `context_load` 层不是问题**——是你设计的必要灵魂注入,砍了会丢个性化。
- **已被截断的风险已解除**:`MEMORY.md` 从 16K 压到 2.3K。
- **最大单点优化在 WorkBuddy 侧**:connector-status 折叠(P0-1)是零风险第一刀。

### 4.3 灵台端可优化点(按性价比)

1. **knowledge_pulse + topics_of_interest(共 ~1,184 字符)改为 on-demand** ✅ 最值得做 ✅ **已实现(2026-07-20)**
   - 这两块是「知识库动态/热点话题」主动推送,并非每问都需。
   - 改为:用户问起相关话题、或每周查等场景才注入,平时不塞。
   - 实现:`server.py` 的 `ensure_context` 新增 `ambient: bool = False` 参数 + `_inject_ambient()` 助手;warm/full/快返三路径统一接开关,缓存本体恒 lean。
   - **实测**:默认 `context_load` 返回 5,206→4,191 字符(省 ~1,015/~670 token),`ambient=True` 时两块仍可取,缓存无污染。
   - 生效条件:MCP server 重启后加载新代码(当前运行进程仍是旧码,本会话 context_load 未变)。
2. **协作者约束集 1,163 字符 → 冻结为「编号+一句话」**
   - 8 条细则全量塞。可改成编号索引+摘要,正文首次触发相关约束时再展开。
   - 省 ~800 字符。需注意:约束集是硬规则,展开逻辑要稳,改动有风险。
3. **画像三层 922 字符 — 保持**
   - 已从源 8.5K 压到 922,且心性.md 源 4.4K 仅部分注入,说明已有摘要逻辑。保持。
4. **机制层已优,不动**
   - `detail="detailed"` 实际走 warm-start 缓存(前面优化记录:延迟 569ms→8.5ms);
   - `pending_count` 30s TTL 缓存。这块无需改。

### 4.4 优先级判断

灵台侧优化**收益小、且部分影响「灵识主动性」设计意图**,不建议大动。
**仅推荐做 4.3-①(knowledge_pulse + topics_of_interest on-demand)**——零风险、省 ~1.2K 字符、无损主动性。
真正的大头仍在 WorkBuddy 侧(connector-status 折叠 + 工具目录懒加载)。
