# 真·死工具分析（2026-07-20）

> 方法论：从**真实注册真源**抓工具集，再与**调用日志** + **别名表**对账。
> 注册真源 = `decorators.REGISTRY`（由 `server_mixins/*.py` + `server.py` 的 `@tool()` 装饰器在导入时填充），`router.py` 自省构建 `_TOOL_MAP` + `_ALIASES` + `_MACRO_TOOLS`。**`tools.py` 与 `apply_all.py` 均不参与运行时注册**（`tools.py` 零 import；`apply_all.py` 是代码生成脚本）。
>
> ⚠️ 与上一版 `dead_tool_check.py` 的本质区别：旧脚本只读死文件 `tools.py`（含 47 个注释桩），虚报 82 注册/41 死工具。本分析读真源。

## 一、规模基线

| 指标 | 数值 |

## 二、Tier 1 — 确认 bug（建议立即修）

### 2.1 两个断裂别名（指向未注册目标）
`router.py` 的 `_ALIASES` 里有两条指向**不存在**的工具：

| 别名 | 指向目标 | 问题 |
|---|---|---|
| `mem_archive` | `memory_archive` | 目标未注册（M6 已合并进 `memory_feedback`） |
| `mem_merge` | `memory_merge` | 目标未注册（M6 已合并进 `memory_feedback`） |

→ 调用 `mem_archive`/`mem_merge` 会解析到 `memory_archive`/`memory_merge`，后者不在 `_TOOL_MAP` → 返回 "Unknown tool" 错误。
**修法**：把两条别名改指 `memory_feedback`，或直接删除这两条别名。

### 2.2 幽灵工具调用：`memory_graduate`
- 全代码库**无任何 `@tool` 注册、无别名**；仅在 `tool_sessions.jsonl` 被调用过 1 次（07-19），且记忆银行明确记着"因 status bug 不可用，毕业须直调 `mem_link`"。
- 这是**被废弃却仍被调用**的悬空引用——某处（技能/AGENTS.md/AI 习惯）还在让它调 `memory_graduate`。
**修法**：搜引用源，统一改成 `mem_link`；MCP 侧确认该名已彻底移除或返回明确弃用提示。

## 三、Tier 2 — 冗余别名（可选清理）

以下工具**既是真实 `@tool` 注册，又是别名目标**——别名被真身遮蔽，是死条目：

`refine_list_sources`→`refine_status` · `refine_all_status`→`refine_status` ·
`raw_derive_batch`→`raw_derive` · `system_search_logs`→`fulltext_search` ·
`system_health`→`health_inspect` · `system_check_status`→`health_inspect`

→ 删 `_ALIASES` 中这 6 行即可（真身 `@tool` 仍正常工作）。

## 四、Tier 3 — "窗口零调用"≠死（重要澄清，勿误删）

43 个窗口内零调用工具里，大量是**活工具被日志盲区掩盖**：

- **宏内部调用（不在顶层日志，但被宏高频调用）**：`user_feedback`/`user_push`/`raw_save` 经 `session_end`（23 次）内部调用；`page_create`/`page_update`/`page_append_section` 经 `refine_quick`/`ingest_ripple_apply` 调用。这些"零调用"是**假象**。
- **`system=True` 管线内部工具（17 个）**：`auto_evolve`/`get_macro_stats`/`knowledge_recall`/`knowledge_domains`/`knowledge_pages`/`knowledge_search_evidence`/`memory_scan_conflicts`/`observation_list`/`observation_rule_health`/`raw_derive_batch`/`refine_all_status`/`refine_list_sources`/`system_check_status`/`system_health`/`system_restart`/`system_search_logs`/`system_token`——由代码/管线调用，不进顶层日志，不能据此判死。

## 五、Tier 4 — 候选真死（需更长观察窗口才能认证）

剔除 Tier 3 的宏内部 + system 后，剩下**暴露给 AI、窗口内零调用、无明显宏依赖**的候选（约 20 个）。**仅候选，不认证**——3 天窗口 + 宏影子效应不足以判死：

| 候选 | 类别 | 备注/疑似后继 |
|---|---|---|
| `agent_feedback` `agent_recommend` `agent_skills` | agent | Agent 推荐特性，疑似未启用 |
| `output_list` `output_publish` | output | 发布特性，疑似未用 |
| `vector_index_status` `domain_visibility` | 基础设施 | 疑似弃用 |
| `knowledge_search_evidence` `knowledge_quality_check` `system_registry_scan` | knowledge/system | 疑似未接入 |
| `topic_match` `lingshi_classify` `cross_end_activity` `episodic_search` | macro/system | 低频/疑似弃用 |
| `page_history` `page_link_suggest` | page | 疑似未用 |
| `knowledge_compound` `memory_project_snapshot` `observation_reflect` | knowledge/memory/observation | 低频但可能 legit |
| `skillopt_adopt` `skillopt_reject` | pipeline | skillopt 写操作（dryrun/run/status/log 在用，adopt/reject 窗口内零） |
| `knowledge_explore` `knowledge_inject` `lingshi_inject` | knowledge/lingshi | 核心探索/注入工具，低频但重要，疑日志窗口偏差 |

## 六、如何真正认证死亡（建议下一步）

1. **拉长调用日志窗口**：当前 `tool_sessions.jsonl` 仅 3 天。建议累计 ≥ 30 天真实调用后再对账。
2. **埋点宏内部调用**：让 `session_end`/`refine_quick`/`knowledge_recall`/`ingest_ripple_apply` 把内部 `user_feedback`/`user_push`/`raw_save`/`memory_write`/页面写操作也记入日志（或单独 macro 埋点），消除影子效应。
3. **源码反向引用核查**：对 Tier 4 候选，grep 全仓库（含 AGENTS.md、技能/、记忆）看是否有调用方；无调用方 + 长窗口零调用 = 可删。
4. **可复现脚本**：本分析逻辑（解析 `@tool` 真源 + 别名 + 日志）应固化成替代 `dead_tool_check.py` 的新脚本，避免再读死文件。

## 七、结论

- **可立即修的真 bug**：2 个断裂别名（`mem_archive`/`mem_merge`）+ 1 个幽灵调用（`memory_graduate`）。这 3 项是确定性问题，低风险高收益。
- **不要动 43 个"零调用"**：其中大量是宏内部 / 管线内部活工具，其余需更长窗口认证。
- **旧 `dead_tool_check.py` 结论作废**：它读的 `tools.py` 是死文件，虚报的 41 个"死工具"里绝大多数（`raw_derive`/`skillopt_*`/`memory_link`/`knowledge_stats` 等）在本分析里是**注册且被调用**的活工具。
