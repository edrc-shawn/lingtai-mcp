# 决策记录规范

> 决策不是真理，是当时条件下的押注。记录的价值不是证明做对了，而是当条件变化时知道该重新想什么。

## 记录时机

每次做技术选型、架构选择、流程改动时，在该内容所属的丹房页末尾追加 `## 决策记录` 区块。

如果一个决策跨多个域，挂在离决策结果最近的页下。

## 记录格式

```markdown
### YYYY-MM-DD 标题 [pending|confirmed|overturned]

| 字段 | 内容 |
|------|------|
| 决策 | 具体选了哪个方向 |
| 选项 | 当时知道的其他可选方案 |
| 约束 | 当时的限制条件（时间/信息/能力） |
| 假设 | 押注成立的前提 |
| 触发重评 | 出现了什么信号就该重新想 |
| 可逆性 | 高（改起来容易）/ 中 / 低（沉没成本高） |
```

### 状态流转

```
pending ──→ confirmed  （假设被验证，决策成立）
   │
   └──────→ overturned （假设被推翻 / 触发信号出现）
                └── 追加 ## 重评记录，记录推翻原因和新决策
```

默认状态是 `pending`。**confirmed 不需要改成一个新条目**——验证通过就在原地加一条重评记录，状态改为 confirmed。

## 重评记录追加格式

当触发信号出现或定期复审时：

```markdown
- YYYY-MM-DD: 触发信号 / 结论 / 新决策
```

## 联动机制

### 观察层
每日内观扫描所有 `[pending]` 决策的触发条件，匹配近期操作日志。命中 → 列到内观报告"待重评决策"区。

### 内观
每日 21:00 内观报告追加"决策重评检查"——列出所有 pending 决策及其信号状态。

## 示例

```markdown
## 决策记录

### 2026-07-07 问知管线不建双管线 [pending]

| 字段 | 内容 |
|------|------|
| 决策 | 日志回溯独立，不建双管线 |
| 选项 | 双管线独立 / 单管线+AI追加 |
| 约束 | 不增维护复杂度、当前日志量不大 |
| 假设 | AI 能可靠判断何时追加 sys_search_logs |
| 触发重评 | AI 连续漏调日志回溯 ≥2 次 |
| 可逆性 | 高（加 system_investigate 几分钟） |
```
